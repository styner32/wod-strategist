# A. 시계(타임라인) 문제

## A-1. [P1] `verify_highlights`가 미디어시계 관측을 캡처시계 청크와 비교한다

**위치**: `api/internal/worker/verify_highlights.go` — `filterLowTargetConfidenceObservations()` (현재 L524~)

**현재 코드**
```go
for _, chunk := range lowConfChunks {
    cStart := 0.0
    cEnd := 0.0
    if chunk.StartSecs != nil {   // ← 캡처시계
        cStart = *chunk.StartSecs
    }
    if chunk.EndSecs != nil {     // ← 캡처시계
        cEnd = *chunk.EndSecs
    }
    if cEnd > cStart && obsStart < cEnd && obsEnd > cStart {
        isLowConf = true
```

**왜 문제인가**
`obsStart`/`obsEnd`는 바로 위 `NormalizeHighlightSegmentsJSON(..., VideoEndSeconds: videoDuration.Seconds())`을 거친 **미디어시계** 값이다. 반면 `chunk.StartSecs`/`EndSecs`는 **캡처시계**다. 두 축이 세션 후반으로 갈수록 최대 52초 어긋나므로, low-confidence 청크와 겹치는지 판정이 틀린다. 즉 **엉뚱한 관측이 제거되고, 실제로 걸러야 할 관측은 남는다.**

**수정 방향**
`chunk.MediaStartSecs` / `chunk.MediaEndSecs`(둘 다 `*float64`, `api/internal/db/db.go` `ChunkAnalysisResult`)를 사용한다. 단, 두 가지를 함께 처리해야 한다.

1. `media_*`가 `NULL`인 행은 매핑이 없으므로 **비교에서 제외**한다(과거 세션). `StartSecs`로 조용히 대체(fallback)하면 지금의 버그가 그대로 재현되므로 금지한다.
2. 마이그레이션 `000038`이 과거 행을 `media_* = start_*`로 backfill 했기 때문에, `media_end_secs = end_secs`인 세션은 "실제로 드리프트가 없는 세션"과 "매핑이 없는 세션"이 구분되지 않는다. 이런 세션은 보정이 불가능하므로 필터를 보수적으로(관측을 제외하지 않음) 동작시킨다. 자세한 배경은 C-3 참조.

**추가할 테스트** (`api/internal/worker/verify_highlights_test.go`)
- 캡처시계와 미디어시계가 50초 어긋난 청크를 만들고, 미디어시계 기준으로 겹치는 관측만 걸러지는지 검증
- `media_*`가 NULL인 청크는 필터에 영향을 주지 않는지 검증

## A-2. [P2] 관측이 전부 걸러지면 태스크가 실패로 끝난다

**위치**: `api/internal/worker/verify_highlights.go` L192 부근

```go
segments = w.filterLowTargetConfidenceObservations(p.SessionID, segments)
if len(segments) == 0 {
    return fmt.Errorf("no highlight segments to verify: %w", asynq.SkipRetry)
}
```

**왜 문제인가**
필터가 정상 동작해 모든 관측이 low-confidence로 판정된 경우는 **정상적인 결과**이지 오류가 아니다. 그런데 위 코드는 이를 태스크 실패로 처리한다. A-1을 고치면 필터가 더 정확해지면서 이 경로에 도달할 확률이 오히려 올라간다.

**수정 방향**
필터 **이전에** 세그먼트가 비어 있던 경우(입력 오류)와, 필터 **결과** 비게 된 경우(정상 종료)를 구분한다. 후자는 하이라이트 없음으로 정상 완료 처리하고 상태를 기록한다.

## A-3. [P1] 시계 변환 계약을 문서화하고 공용 변환기를 만든다

**위치**: `docs/polar-sensor-pipeline-plan.md` §1.1 "시간축 계약"

**현재 문서의 틀린 서술**
> "pause를 제외하는 것은 `merged.mp4`의 media time 뿐이고, 그 매핑을 `pause_intervals`가 담당한다."

**왜 틀렸나**
위 실측 세션이 반증한다. 일시정지 0회인데도 52.31초가 벌어졌다. `pause_intervals`는 사용자 일시정지만 담고, 청크 경계 공백(278ms × 188)은 담지 못한다.

**수정 방향**

1. 계약을 다음으로 교체한다.
   - 센서 NDJSON의 `t`, `chunk_analysis_results.start_secs`/`end_secs` = **캡처시계**(사람 기준 실제 경과시간)
   - `merged.mp4` 재생 위치, `media_start_secs`/`media_end_secs` = **미디어시계**
   - 두 축의 변환은 **청크별 구간 선형 매핑**으로만 가능하다. `pause_intervals`는 사용자 일시정지 구간 표시용이며 변환에 쓰지 않는다.
2. 변환 함수를 한 곳에 만든다(제안: `api/internal/worker/` 또는 `api/internal/` 공용 패키지).
   ```
   captureToMedia(sessionID, captureSecs) -> (mediaSecs, ok)
     - 해당 캡처 시각을 포함하는 청크를 찾아 media_start + (capture - start)
     - 어떤 청크에도 속하지 않으면(청크 경계 공백) ok=false
     - media_* 가 NULL이거나 media_end == end 인 세션은 ok=false
   ```
   경계 공백에 떨어지는 샘플은 전체의 약 2.7%(52초분)이며 **대응하는 영상 프레임이 존재하지 않는다.** 호출부는 가장 가까운 경계로 붙일지 결측으로 둘지 명시적으로 정해야 한다.
3. 용도별 사용 규칙을 문서에 표로 남긴다.

   | 대상 | 시계 |
   |---|---|
   | 하이라이트 클립 구간, 하드섭 자막, 재생 seek | 미디어시계 |
   | 심박·가속도·피로도·페이싱 등 사람 기준 지표 | 캡처시계 |
   | 센서를 영상 위에 겹치기 | 캡처 → 청크별 매핑으로 변환 |

**검증 쿼리** (드리프트가 선형으로 쌓이는지 눈으로 확인)
```sql
SELECT row_number() OVER (ORDER BY start_secs) AS n,
       round(start_secs::numeric, 2)                      AS capture_start,
       round(media_start_secs::numeric, 2)                AS media_start,
       round((start_secs - media_start_secs)::numeric, 2) AS drift
FROM chunk_analysis_results
WHERE session_id = 'WOD-20260907-01M1WR2J23FBA55T1M1H2F2NVN'
ORDER BY start_secs;
-- drift가 0 → 52.31로 선형 증가하고, 행간 증가폭이 ≈0.278이면 정상
```

## A-4. [P2] 센서 `dt`를 요청 샘플레이트가 아닌 기기 타임스탬프에서 산출한다

**위치**: `features/health/polar/polarPmdProtocol.ts` — `parseAccPacket()`의 `const dt = Math.round(1000 / context.accHz);`

**실측**
| 값 | 측정 |
|---|---|
| 요청 샘플레이트 | 50 Hz (`dt` = 20 ms로 기록 중) |
| 실제 스트림 | 패킷당 36샘플, 패킷 간 703 ms → 샘플 간 **19.53 ms (51.2 Hz)** |
| 결과 | 패킷 내부에서 최대 **16 ms**(약 1샘플) 앞당겨 기록됨 |

패킷마다 기기 타임스탬프로 앵커가 재설정되므로 오차는 **누적되지 않지만**, 패킷 내부 배치가 계통적으로 늘어난다.

**수정 방향**
Polar SDK의 `PmdTimeStampUtils.getTimeStamps(previousFrameTimeStamp, frameTimeStamp, samplesSize, sampleRate)` 방식을 따른다. 즉 이전 패킷 타임스탬프와 현재 패킷 타임스탬프 사이를 샘플 수로 등분해 `dt`를 구하고, 이전 패킷이 없을 때만 `1000/accHz`로 폴백한다. `PmdStreamContext`에 직전 패킷의 `deviceMs`를 보관해야 한다.

**주의**: `stream_start` 이벤트의 `sampling.acc_hz`는 협상값(50)을 유지하고, 실제 산출된 `dt`는 `acc` 라인에 이미 들어가므로 스키마 변경은 필요 없다.

**테스트**: `polarPmdProtocol.test.ts`에 연속 두 패킷을 주고 `dt`가 기기 델타 ÷ 샘플 수로 나오는지, 첫 패킷은 폴백값을 쓰는지 검증.

## B-4. [P2] 스트레칭 자동 등록이 실패해도 무시하고 추천에 넣는다

**위치**: `api/internal/worker/stretch_recommendations.go` L402-411

```go

    VALUES (?, ?, ?, ?, ?, ?, '', '')
```

`stretches` 테이블에는 길이 CHECK 제약이 있다(`000046_create_stretches.up.sql`): `name` 1~120, `description` ≤4000, `duration_hint` ≤200, `caution` ≤1000. 위 INSERT는 **LLM이 만든 원문을 길이 검사 없이** 넣으면서 오류를 `_ =`로 버린다. 제약 위반으로 INSERT가 실패해도 `resolver`에는 이름이 등록되고 추천이 반환되므로, **카탈로그에 없는 스트레칭을 추천**하게 된다.

**수정 방향**: INSERT 전에 각 필드를 제약 길이에 맞춰 자르거나 검증하고, 오류를 확인해 실패 시 `resolver` 등록과 추천 반환을 건너뛴다. 오류는 로깅하되 클라이언트에 원문을 노출하지 않는다(`api/AGENTS.md`의 정보 노출 규칙).

## B-5. [P3] `related_wods`의 ILIKE 프리필터가 정규화와 어긋난다

**위치**: `api/internal/controllers/related_wods_handlers.go` L211

```go
Where("normalized_workout ILIKE ?", "%"+targetMovement+"%")
```

점수 계산은 `movement.NormalizeKey`로 하는데 SQL 프리필터는 **원문 문자열**을 그대로 쓴다. `"Pull up"` / `"Pull-up"` 같은 하이픈·공백 변형이 점수 계산 전에 걸러진다. 또한 입력에 `%`나 `_`가 들어오면 LIKE 와일드카드로 동작한다.

**수정 방향**: 프리필터에도 `NormalizeKey`를 적용한 값을 쓰고, LIKE 특수문자(`%`, `_`, `\`)를 이스케이프한다.

## B-7. [P2] 비디오 캐시 프루닝이 만료 파일 하나로 임계값을 바꾼다

**위치**: `features/video/videoCacheManager.ts` L360-370

```ts
const targetSize = maxBytes * 0.8;
let prunedCount = 0;
for (const item of sortedOldestFirst) {
  const isExpired = maxAgeMs > 0 && now - item.modifiedTime > maxAgeMs;
  const isOverSize = totalSize > maxBytes || (prunedCount > 0 && totalSize > targetSize);
  ...
}
```

나이 때문에 만료된 파일 **하나만 지워져도** `prunedCount > 0`이 되어, 이후 모든 파일에 대해 판정 기준이 `maxBytes`에서 `maxBytes × 0.8`로 바뀐다. 한도 미만인 캐시(예: 1.5GB 한도에 1.3GB)가 1.2GB까지 정리되면서 **최근 영상이 삭제**된다.

**수정 방향**: 크기 초과로 프루닝이 시작됐을 때만 headroom 목표를 적용한다. 만료 삭제와 크기 초과 삭제의 상태를 분리한다(`sizePruningStarted` 같은 별도 플래그).

# C. 수정 항목은 아니지만 인지해야 할 것

> C-2(배터리 소모)는 분석과 실험 설계가 커져 **D절로 승격**했다. ID는 혼선을 피해 그대로 비워 둔다.

## C-1. Phase 0.2(실기기 원본 덤프)는 여전히 미완료

`features/health/polar/__fixtures__/h10-*.json`은 Polar SDK 레이아웃에 맞춰 **손으로 만든 합성 데이터**다(각 파일 `description`에 경고 표기). 다만 위 실측 세션으로 다음이 간접 검증됐다.

| 검증 | 결과 |
|---|---|
| 프레임 타입 | 실기기는 `frame_type: 1, delta_compressed: false` (비압축 TYPE_1, 16비트) |
| ACC 디코딩 | 가속도 크기 \|a\| 중앙값 **1.019 g** (중력 1.0 g 대비 1.9% 오차) |
| RR 파서 | RR 유도 심박 vs 기기 보고 BPM 차이 **중앙값 −0.1 bpm** |
| 기기 시계 | 타임스탬프가 2019년을 가리킴 → 앵커링 없이는 변환 불가함이 실증됨 |

**delta 압축 경로는 실기기에서 한 번도 실행되지 않았다.** 압축 프레임 디코더는 여전히 미검증이다.

## C-3. 과거 세션은 시계 변환이 불가능하다

마이그레이션 `000038_create_chunk_reanalysis_runs.up.sql`이 기존 행을 `media_start_secs = start_secs`, `media_end_secs = end_secs`로 backfill 했다. 즉 2026-07-15 이전 세션은 **드리프트가 0으로 잘못 기록**돼 있고, 청크 파일이 수명주기 정책으로 지워졌다면 소급 보정도 불가능하다. A-3의 변환기는 `media_end_secs ≠ end_secs`인 세션에만 유효하다.

# D. 배터리 소모 — 측정 먼저, 대책은 그 다음

## D-0. 지금까지 안 것

실측: `battery_percent_start: 100` → `battery_percent_end: 90`, 31.9분 = **시간당 약 18.8%p**(연속 5.3시간이면 방전).

계획서에서 "`0x2A19`는 1% 스텝이라 20분 세션에선 0~1% 변화, 파생 지표는 노이즈"라고 판단해 드레인 지표를 v1에서 제외했는데 **그 판단은 틀렸다.**

같은 세션에서 계산한 BLE 페이로드 분해:

| 스트림 | 페이로드 | 비중 |
|---|---|---|
| ACC (36샘플 × 6B, 704ms 간격) | 307 B/s | **97.9%** |
| HR/RR | 6.6 B/s | 2.1% |

## D-1. [P2] 배터리 시계열을 NDJSON에 기록한다 — 다른 모든 판단의 전제

**위치**: `features/health/polar/polarSensorRecorder.ts` — `setBattery()`

현재 `setBattery`는 state만 갱신하고 파일에는 쓰지 않는다. 그래서 NDJSON에는 **시작·끝 2점만** 있고 방전 곡선이 없다. 선형인지, 특정 구간에서 급락하는지, 부하가 사라지면 회복하는지 알 수 없다.

```ts
setBattery(percent: number): void {
  const changed = state.batteryLatest !== percent;
  state.batteryLatest = percent;
  if (state.isActive && state.batteryStart === undefined) {
    state.batteryStart = percent;
  }
  if (changed && state.isActive) {
    state.writer?.writeImmediate({
      k: "battery",
      t: Math.max(0, Date.now() - state.baseEpochMs),
      percent,
    });
  }
}
```

`k: "battery"` 이벤트를 NDJSON 포맷 문서(§3)에도 추가한다. 테스트는 값이 바뀔 때만 줄이 쓰이는지(같은 값 반복 시 기록 안 됨) 검증한다.

## D-2. 샘플링 감소가 답인지는 아직 알 수 없다

**방향은 맞다.** ACC가 BLE 페이로드의 97.9%이므로 줄이면 줄어든다.

**다만 절감은 선형이 아니다.** BLE 소모를 지배하는 것은 페이로드 바이트가 아니라 무선을 깨우는 횟수(connection event)다. 216B는 이미 한 이벤트에 들어가는 크기이고, 25Hz로 낮추면 패킷 간격이 704ms → 1408ms가 되지만 연결 유지용 빈 이벤트는 계속 발생한다. **50%가 아니라 25~40% 절감**을 기대하는 편이 현실적이며, 실측으로 확인해야 한다.

**그리고 19%가 진짜 소모인지부터 불확실하다.**

1. **코인셀 전압 강하 가능성.** H10 잔량은 전압 추정값인데, CR2025는 내부 임피던스가 커서 무선 부하가 걸리면 전압이 처졌다가 부하가 사라지면 회복한다. 종료 직후 읽은 90%가 일시적 sag일 수 있다.
2. **대조군 없음.** ACC 없이 HR만 켠 같은 길이 세션의 소모율을 모른다. 증가분을 ACC 탓으로 돌릴 근거가 아직 없다.
3. **배터리가 노후했을 가능성.** baseline이 이미 높으면 샘플링 조정은 헛수고다.

**가장 싼 검증**: 세션 종료 후 **10~30분 뒤 배터리를 다시 읽는다.** 97~100%로 돌아오면 sag이므로 샘플링을 건드릴 이유가 없다. 90% 근처를 유지하면 실제 소모다.

## D-3. 샘플링 외의 지렛대 (실험 설계 시 함께 고려)

- **일시정지 중 스트림 중단** — 현재는 pause 중에도 계속 흘린다(회복 심박 관측을 위한 의도된 설계). 휴식이 긴 WOD라면 절감 효과가 샘플레이트 조정보다 클 수 있고, 데이터 손실이 "쉬는 구간"에 한정된다.
- **delta 압축** — 실기기가 `delta_compressed: false`(비압축)로 보낸다. 압축이 켜지면 페이로드가 크게 준다. 해상도·범위 조합 때문인지 조사할 가치가 있다. 참고로 이 때문에 압축 디코더 경로는 실기기에서 한 번도 실행된 적이 없다(C-1).
- **connection interval** — `Device.requestConnectionPriority(ConnectionPriority.LowPower)`가 `react-native-ble-plx`에 있으나 **Android 전용**이다. 실측 세션은 iOS(`app.platform: "ios"`)라 이 레버는 쓸 수 없다.
- **8비트 해상도(TYPE_0)** — 페이로드 절반. 정밀도 손실과 맞바꾼다.

## D-4. 권장 실험

같은 스트랩·같은 배터리로, 각 조건 사이에 **30분 휴지**를 두어 전압 회복분을 분리한다. D-1 로깅이 먼저 들어가야 의미 있는 데이터가 나온다.

| 조건 | 알 수 있는 것 |
|---|---|
| HR만 (ACC 미시작) 20분 | baseline 소모율 |
| ACC 50Hz 20분 | ACC의 순증가분 |
| ACC 25Hz 20분 | 샘플링 절감의 실제 기울기 |
| 각 세션 종료 30분 후 재측정 | sag vs 실제 소모 판별 |

# 우선순위 요약

**정렬 기준은 "틀린 값이 저장·표시되는가"다.** 그래서 B-3(피로도 가중치 비결정성)을 원래 P2에서 **P1으로 올렸다** — 같은 입력에 매번 다른 RPE가 나오는 것은 계산 정확도 문제의 정중앙이다. 반대로 B-1(권한)은 실제 취약점이지만 이번 단계 초점 밖이라 E-1로 보류했다.

| ID | 우선순위 | 범위 | 한 줄 요약 |
|---|---|---|---|
| A-1 | P1 | 백엔드 | 미디어시계 관측을 캡처시계 청크와 비교 — 잘못된 관측이 걸러짐 (실동작 버그) |
| A-3 | P1 | 문서+백엔드 | 시계 변환 계약 교체 및 공용 변환기 도입 |
| B-3 | **P1** | 백엔드 | 피로도 가중치가 실행마다 달라짐 — 같은 입력에 다른 RPE |
| A-2 | P2 | 백엔드 | 필터 결과 공집합을 태스크 실패로 처리 |
| A-4 | P2 | 모바일 | 센서 `dt`를 기기 타임스탬프 델타에서 산출 (샘플 배치 오차 16ms) |
| B-2 | P2 | 백엔드 | mobility `Assessable` 하드코딩 — 판정 불가 관측이 추천에 반영됨 |
