# Recording media preparation

## Admission and compatibility

- Migration `000063_recording_media_pipeline` must precede API/worker deployment. It adds `recording_media_runs`, `recording_chunks`, `chunk_media_preparations`, and `analysis_video_preparations`; schema constraints belong to that migration, not gorm tags.
- New captures opt in only with `EXPO_PUBLIC_MEDIA_PIPELINE_VERSION=1`. The default is off. `OriginalCapture` freezes the version at capture start; existing recordings, old queued work, and direct file uploads keep their legacy path. Legacy admission is latched as run `version=0/state=LEGACY`; never promote a previously accepted session to v1.
- v1 `/chunk-complete` requires `media_pipeline_version: 1`, stable `client_chunk_id`, 1-based `capture_order`, and a valid capture interval. Each physical upload uses a unique object name; successful PUT followed by failed notification retries only the notification. Recovery retains the logical ID/order even when uploading the original instead of a compressed copy.
- Receipts expose `chunk_id`, `source_generation`, and `gcs_uri`. IDs/generations cross the JavaScript boundary as decimal strings. The first accepted source object/generation is immutable. Repeat logical IDs return its prior receipt; conflicting order/interval returns 409.
- `handleRecordingMediaChunk` must never call GCS (`ListObjects` or `ObjectAttrs`) inside `db.WithSessionAutomaticWork` (`profiles FOR UPDATE`): run a read-only DB precheck first, resolve legacy/source GCS metadata outside any transaction, and re-verify inside the short commit transaction.
- v1 `/merge-chunks` requires `expected_chunk_count` and ordered `chunks: [{chunk_id, source_generation}]`. This list must equal every admitted chunk with contiguous capture order. Sealing rejects future new chunks/source replacements; retries reuse the stored manifest. Unsealed recordings are never reconstructed from a GCS listing.

## Work and media evidence

- `media:prepare_chunk` runs on `media:chunk`; `media:merge` and `media:prepare_analysis` share `media:session`. Each queue has a dedicated Asynq server with concurrency 1. `media:coordinate` uses `default` and exits while dependencies remain pending; it never holds a worker waiting for child media work.
- Initial task timeouts: chunk preparation 5 minutes, coordinator 1 minute, merge 60 minutes, analysis preparation 45 minutes, existing full AI analysis 60 minutes. New media commands limit decoder/encoder/filter threads to 1 and do not nest the legacy parallel chunk-preparation pool.
- Source reads pin GCS generation. Preparations are keyed by source generation, `concat-v1`, and requested output profile. Native upright-resolution preparations are reused only when their actual dimensions/audio match the final `concatPreparationSettings`; mismatches are prepared again from the original. Preserve homogeneous resolution, mixed-input 1280px cap, relative audio placement, silence padding, and exact video-owned duration.
- Source profile/timeline and leading-black evidence are reusable for the same immutable source. Black detection retains the existing first-0.35-second probe and bounded trimming policy. AI chunk success is not media readiness.
- Persisted signatures use `framehash-murmur3-sha256-tb30000-v1`, explicit frame count/digest/start/end, and every frame's `pts`/`duration`. `videoFrameSignature.timings` is unexported: use the stored DTO rather than directly JSON-marshaling that struct. Merge still verifies the full decoded frame order, per-frame timing, and A/V/container endpoints.
- All derived artifacts live under `videos/{pid}/{sid}/derived/`. Original-source discovery must exclude that exact relative subtree. Immutable attempt names prevent stale uploads overwriting a published artifact. Verified staging is copied to `merged.mp4` with generation preconditions and run/manifest metadata; encoding/uploading does not hold the session publication lock.
- Verified cumulative intervals are saved in the run before chunk AI is terminal. Before full analysis/activity review dispatch, finish the existing AI terminal/orphan checks and publish these intervals to `chunk_analysis_results.media_start_secs/media_end_secs`. Capture-clock offsets never substitute for verified merged-media offsets.
- `h264-720w30-crf28-aac64-v1` analysis preparation encodes only above `1000 << 20` bytes, and enforces the `1 << 30` hard limit. A failed encode may use the original only within that hard limit. Prepared v1 input is shared by optimized/legacy full analysis and bypasses the old inline re-encode. More than 90 minutes retains merged playback but skips analysis preparation/AI/activity review.

## Recovery and validation

- Media tasks use `MaxRetry(0)`; durable rows own up to 3 attempts, with 30-second then 2-minute backoff. Recovery runs at startup and every 15 seconds. Leases last 2 minutes with 30-second heartbeats; publication requires the current token and source/manifest identity. Full AI retains Asynq retry ownership and reuses prepared media; stale dispatch epochs and already published completion must stop before paid calls.
- Use the existing session work/publication guards and active-work checks for new queues/outboxes. Archive/cancel fences also cover recovery and late results; restore never resumes original automatic work. Explicit retry resumes the failed stage from retained immutable checkpoints. During `RECORDING` recovery sweeps (`every 15s`), `DispatchRecordingMedia` checks `EXISTS` for undispatched AI chunks or due `PENDING` `chunk_media_preparations` read-only before taking `WithSessionAutomaticWork` so active captures do not contend on `profiles FOR UPDATE`.
- Cost-bounded validation uses short fixtures (at most five 10-second chunks plus a 2-second tail), small media edge-case fixtures, and DB/Redis-only 238-chunk orchestration. Provider/storage responses use existing `MockTransport`; no real Gemini calls or 39-minute cloud benchmark is required. This does not establish long-duration latency, memory stability, or physical-device acceptance.
- Mobile validation completed during implementation: targeted `features/wod/api.test.ts` and `app/workout/__tests__/visionTestPage.original.test.tsx` passed 81 tests; `npm run typecheck` passed. Backend and deployment-image results are recorded below.
