# WOD onset, full-session scoring and training load

Implementation version 1 applies only to newly registered `workout_type: wod` sessions. Migration `000055` adds `profiles.wod_tracking_started_at` (database-clock rollout/profile creation time; read-only in Gorm), `sessions.wod_evaluation_version` (existing rows remain 0), nullable `sessions.effort` (integer 1–10), and nullable `session_reanalysis_runs.wod_start_request`.

- Explicit session creation opts new sessions into evaluation version 1. The recording/video worker creates missing WOD session rows; it checks the earliest existing chunk/analysis timestamp against the profile's tracking start, so old rowless recordings remain version 0. Existing version 0 sessions are never upgraded automatically. Verified pre-rollout ULIDs also exclude delayed mobile uploads.
- New WODs use the two-pass path even if the worker's legacy mode is configured. Every indexed exercise segment is deeply analyzed; the legacy segment budget/triage remains on old/non-WOD paths. Whole-session scoring is a separate text-only `ParseText` call over validated `wod_evidence`, excluding prior-score history. Expect added onset/synthesis calls and greater latency for many-set videos.
- Onset is visually revalidated using the original uploaded source. A returned timestamp must lie inside an indexed exercise interval, identify the target, and have visible preceding rest/setup (unless time zero). HR is optional and never sufficient for onset. Only current source-matched timeline readings are mapped through verified capture/media pairs. Missing sensor data does not delay video processing.
- `session_score.evaluation_version: 1` adds `wod_start` (`seconds`, `end_seconds`, optional `elapsed_seconds`, `status`, `source`, `evidence`) and `evidence_status`. Start/end are original-media seconds. The end is the last successfully validated exercise observation, not an inferred completion signal. Elapsed duration uses verified capture-clock endpoints when available, retaining camera pause/rest gaps; otherwise it uses original-media elapsed time.
- All supplied observations are made relative to WOD onset for synthesis, so prepended waiting does not dilute the scoring input. Set-to-set gaps remain in the input and must be interpreted in light of EMOM/other WOD structure. Unknown/unanalysed intervals are not assumed to be rest. Partial coverage suppresses intensity and consistency and leaves duration unresolved.
- Scores are nullable; missing intensity must not become a default muscle-load factor. General overall weights are form/intensity/consistency 0.5/0.3/0.2, strength/skill weights 0.7/0.15/0.15. Server recomputes rounded overall; any required missing dimension leaves overall null. Legacy numeric records remain readable and untouched.

## APIs and UI

- `GET /api/v1/sessions/:session_id/wod-training`: eligible, effort, score, wod_start, session_load. Effort is independent of AI score and survives re-analysis.
- `PUT /api/v1/sessions/:session_id/effort`: `{ "effort": 1..10 }`, exact owner/profile scope, eligible new WOD only. Reject missing/null/fractional/out-of-range values. This never invokes AI or changes scores.
- `GET /api/v1/wod-training-load?profile_id=...&timezone=Asia/Seoul`: owner-scoped seven/twenty_eight windows and optional change_percent. Any IANA timezone is accepted; default Asia/Seoul.
- Session load (AU) = elapsed WOD seconds / 60 × manual Effort. Each window includes today and the preceding 6/27 local calendar days; daily averages divide by 7/28 including rest days. Change = `(seven.daily_average / twenty_eight.daily_average - 1) * 100`. This is our defined rule, not a replica of Apple's proprietary weighting.
- Only eligible, non-archived WODs count. Unrated, pending/failed analysis, unresolved duration or unknown workout timestamp are missing records, not zeros. Comparison is withheld for missing records, fewer than 28 tracking calendar days, or a zero baseline. Tracking starts at the earlier of `profiles.wod_tracking_started_at` and the earliest `workout_at` of a non-archived version-1 WOD (a promoted legacy WOD). Version-0 WODs in that added pre-rollout period are missing records, counted as `unevaluated_legacy_workouts`, until their version-1 reanalysis is applied. Version-0 WODs dated after rollout stay excluded as before. Totals are always labeled as confirmed records only. Workouts outside this app are not observed.
- Existing re-analysis POST accepts optional `wod_start_secs`: number = manual override, null = restore automatic, omitted = retain current manual setting. Stored request is replayed on retries. JSONB stores `{ "seconds": null }` for reset, a number-valued object for manual start, and SQL NULL for omission; do not store a bare JSON null through NullableJSONDocument. Re-analysis is available to authenticated owners of any session (see [video-analysis.md](video-analysis.md#whole-session-debug-re-analysis)); ownership, one active run and rolling 24h quota (`20` default, `SESSION_REANALYSIS_DAILY_QUOTA` validated at startup) still apply. `wod_start_secs` is accepted for all WOD sessions (including legacy `wod_evaluation_version == 0` sessions; rejected only when an existing `sessions` row has a non-WOD `workout_type`).
- Whole-session WOD reanalysis (`HandleSessionDebugReanalysisTask`) always runs the Version-1 WOD evaluation pipeline (`detectWODStart`, `wodSegmentEvidencePrompt` with fallback to `workout_observations` intervals via `wodEvidenceFromObservedIntervals`, and `synthesizeWODWithProgress`). When `POST /api/v1/sessions/:session_id/reanalyses/:run_id/apply` applies a Version-1 WOD candidate (`evaluation_version == 1`), it promotes `sessions.wod_evaluation_version = 1` (upserting the `sessions` row if missing), and backfills `analysis_results.workout_at` / `workout_at_source` via `timeline.ResolveWorkoutAt` if NULL, so the promoted session participates in Effort editing and WOD training load. It never changes `profiles.wod_tracking_started_at`: that column is the rollout time used by automatic versioning (`ensureWODEvaluationSession`). The upsert of a missing `sessions` row never updates another profile's row (`ON CONFLICT ... WHERE sessions.profile_id = ?`; 409 otherwise).
- Web details show the start marker and editing controls, manual Effort and load comparison. Start correction creates a candidate, then applies the successful candidate automatically; polling can resume without a new AI request. Auto-apply may be cancelled. A changed original score/output rejects a stale candidate with 409. App history exposes Effort editing and load comparison; start editing is web-only.

## Polar H10 Hybrid Activity Intensity (`CalculationVersion = 3`, Migration `000058`)

- **Scale separation**: `sessions.effort` (`1–10`) and `GET /api/v1/wod-training-load` remain strictly manual Effort × confirmed duration. Sensor `hybrid_intensity` (`0–100`) and `hybrid_load_au` (`AU`) are separate objective activity metrics stored in `analysis_results.sensor_summary.metrics.hybrid` and exposed via `HeartRateSummaryDTO.Hybrid` (`heart_rate.hybrid`). Never overwrite `sessions.effort` with sensor scores.
- **Schema (`000058_add_hybrid_sensor_calibration`)**:
  - `profiles.resting_hr_bpm` (`SMALLINT`, `30..120`, nullable; editable via `POST /api/v1/profiles` and `PUT /api/v1/profiles/:id` with `resting_hr_bpm` / `clear_resting_hr`).
  - `profiles.sensor_enmo_rest_g`, `sensor_enmo_ref_g`, `sensor_calibration_version`, `sensor_calibrated_at`, `sensor_calibration_sessions` are marked `gorm:"->"` on `db.Profile` so `ProfileRepository.Update` (`db.Save`) never overwrites worker-promoted calibration.
- **Frozen inputs (`PrepareSensorUpload` when `calculation_version == 3`)**:
  - Snapshots `resting_hr`, `enmo_rest_g`, `enmo_ref_g`, and `calibration_version` into `sensor_processing.calculation_inputs`. Never normalize by single-session peak HR or peak acceleration.
  - Missing `resting_hr_bpm` or `max_hr` is never guessed (e.g., no `60 bpm` fallback): `heart_intensity`, `hybrid_intensity`, and `hybrid_load_au` stay `null` with `"missing_resting_hr"` / `"missing_max_hr"` in `quality_flags`, while `motion_intensity` and ENMO percentiles still compute. `motion_intensity` is the RMS of $M_k$ over every valid ACC second whether or not resting HR is set, so it does not change when HR contact drops or a profile edit adds resting HR; `heart_intensity`/`hybrid_intensity` cover only seconds where HR and ACC are both valid. The UI explains `missing_resting_hr`, `missing_max_hr`, `invalid_hr_reserve_range`, `peak_hr_exceeded_max`, `sensor_data_unreadable`, `no_valid_hybrid_windows` and `low_hybrid_coverage` from `HYBRID_FLAG_KEYS` in `shared/heartRateSummary.ts` (one list for app and web).
  - Cold-start ENMO defaults to `bootstrap_chest_v1` (`enmo_rest_g = 0.01`, `enmo_ref_g = 0.30`, flag `"bootstrap_motion_calibration"`). After $\ge 3$ completed v3 sessions with `valid_acc_seconds >= 120`, `maybePromoteProfileENMOCalibration` promotes the profile once (`WHERE sensor_calibration_version IS NULL`) to `personal_chest_v1` using median 5s-ENMO P05 (`[0.005, 0.05]g`) and P95 (`[max(rest+0.08, 0.12), 1.50]g`) for future sessions only.
- **Formulas (`hybrid-0.75-0.25-gamma2`, `api/internal/sensor/hybrid_metrics.go`)**:
  - Per non-paused 1s bucket $k$, 5s rolling window (`[max(0, k-4), k]` within the same `streamID`): $H_k = \operatorname{clip}_{0,1}((\overline{HR}_k - HR_{\mathrm{rest}})/(HR_{\max} - HR_{\mathrm{rest}}))$, $A_k = \sum \max(\|a_i\| - 1, 0) / N_k$ (raw gravity-included `g`), $M_k = \operatorname{clip}_{0,1}((A_k - A_{\mathrm{rest}})/(A_{\mathrm{ref}} - A_{\mathrm{rest}}))$.
  - When both HR and ACC are `StatusValid` at second $k$: $X_k = 0.75 H_k + 0.25 M_k$, $I_k = 100 X_k$. Missing/invalid buckets are excluded from both numerator and valid-time denominator (no `0` imputation or `×0.5` penalty); `data_coverage = valid_hybrid_seconds / active_workout_seconds`.
  - Cumulative load integrates **1-second step duration** $\Delta t_{k,\min} = \text{bucketDurMs}_k / 60000$ (never 5s): $L = \sum_k X_k^2 \Delta t_{k,\min}$ (`AU`), and session summary uses RMS $I_{\mathrm{session}} = 100\sqrt{L / T_{\mathrm{valid},\min}}$.

Automated checks do not establish onset-model accuracy, real exercise Effort calibration, deployment, or iPhone acceptance. Release order: apply migration, deploy API/worker, then deploy web/mobile. There is no automatic historical backfill; a legacy WOD joins only through an explicitly applied version-1 reanalysis.
